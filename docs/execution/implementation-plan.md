### 前置条件

- 设计规格已定稿 ✅
- v3.1 System Prompt 可用作 Layer 3 + 4 的原材料 ✅

### 任务清单

### 交付物

- `web-app/supabase/functions/anthropic-diagnose/index.ts` — 新版 Edge Function（含四层 Prompt + 条件注入逻辑）
- `test/diagnose.sh` — 五状态单轮 + 多轮流转 curl 测试脚本
- 测试记录：5 状态 × 3 段文字 = 15 轮单轮测试结果
- 测试记录：12 条流转路径全部可达的验证日志
- 归档：v3.1 System Prompt 原文保留为 `docs/superpowers/archive/v3.1-system-prompt.md`

### 关键设计决策

1. **Layer 3 + 4 不动 v3.1 原文**——诊断协议和故障处理是经过验证的，只改入口信号区分（写作中 vs 写完了）
2. **Layer 0 + 1 + 2 是新写的**——这三个层在 v3.1 中不存在，需要从零编写
3. **条件执行逻辑放在 Engine 层**——不在 Prompt 内做条件，而是 Edge Function 代码读取用户输入后决定注入哪些层。理由：Prompt 内条件执行不可靠，LLM 可能在不需要时"自行激活" Layer 3
4. **状态判定采用单轮启发式预分类**——Engine 在调用 LLM 前先以简单规则粗判状态，按判定结果注入对应层，一次 LLM 调用完成。避免两轮调用（先判状态→再诊断）带来的延迟翻倍和成本翻倍：

   | 启发式条件 | 预判状态 | 加载层 | Token |
   |-----------|---------|--------|-------|
   | 输入 < 20 字，无具体名词/动词 | 空虚 | L0+1+2 | ~900 |
   | 有方向词但无场景/人物/动作 | 模糊念头 | L0+1+2 | ~900 |
   | 输入 > 50 字，含叙事元素 ≥ 2 项 | 写作中 | L0+1+2+3 | ~3900 |
   | 用户消息含"不对"/"还是不对"或连续提交差异 < 20% | 卡住了 | L0+1+2（首轮）+ L4（否定时） | ~900 / ~2400 |
   | 用户消息含"你觉得怎么样"/"会不会太…" | 写完了 | L0+1+2+3 | ~3900 |
   | 无法判定 | 写作中（安全默认） | L0+1+2+3 | ~3900 |

   启发式预分类允许误判——LLM 收到 Layer 1 状态确认规则后会在首句公开判断状态，用户纠正即可。误判的成本远低于两轮调用的延迟和费用。

### 关键设计决策

1. **公众号用服务号而非订阅号**——需要客服消息能力（用户发消息后 48h 内可回复）。成本：300 元认证费/年
2. **小程序不实现支付**——按设计规格，小程序只做试用引流，付费闭环在 Web App
3. **跨端框架选择**：如果小程序 UI 简单（一个输入框 + 诊断展示），直接用微信原生框架最快。如果后续计划复杂化，可考虑 Taro（React 语法，复用 Web App 组件）。**Phase D 先用原生**，后续迁移成本不高
4. **消息服务部署位置**：优先用 Supabase Edge Function（与诊断 API 同仓库、同部署），除非微信服务器要求国内 IP（则用腾讯云函数）
