# 产品 MVP 方案：写作诊断工具

> 目标：把 21 个 skill 文件压缩成一个能独立运行的诊断产品。用户贴文字 → 拿诊断报告。

---

## 一、产品定义

### 一句话

一个网页，用户粘贴文字，点击"诊断"，拿到一份包含 X→Y→Z + 铁三角的写作诊断报告。

### 用户是谁

正在写作的人——写小说的、写文章的、写自媒体的。他们有一个共同点：**写了一段文字，感觉不对，但说不出哪里不对。**

### 用户得到什么

```
┌─────────────────────────────────┐
│        📋 写作诊断报告           │
│                                 │
│  🔍 你的文字读起来：[X 效果]     │
│     [用非术语的一句话解释]        │
│                                 │
│  🧠 问题出在：[Y 缺陷]           │
│     [不是写作技法——是执行层的缺口] │
│                                 │
│  🪜 下一步：[Z 推进]             │
│     [一个具体问题——你回答完]      │
│     [就知道该怎么改]              │
│                                 │
│  📐 铁三角健康度：               │
│     因果功能  ████░░░░ 松 → ?   │
│     人物真实  ████████ 紧       │
│     读者张力  ████░░░░ 松 → ?   │
│                                 │
│  ⚡ 如果这个诊断没帮到你：        │
│     [追问入口]                   │
└─────────────────────────────────┘
```

### 用户不用知道的东西

- 不出现"X"、"Y"、"Z"这些字母
- 不出现"铁三角"这个词（实在要用说"三个维度"）
- 不出现"荣格八维"、"认知功能"、"原型"、"哲学透镜"
- 不出现"破冰者/同路人/场景架构者/引爆器/追问者"这些侧面名称

**他只看到一个东西：我的文字出了什么问题，下一步怎么做。**

## 二、从 Skill 到产品：要砍掉什么

你的完整 skill（21 文件，1001 行）是一个**多轮对话写作教练**。但产品 MVP 是**单次诊断工具**。所以大部分东西要砍掉。

### 砍掉（MVP 不用）

| 文件 | 内容 | 为什么砍 |
|------|------|---------|
| personas/ 全部 6 个文件 | 五侧面角色系统 | 单次诊断没有"角色切换"——只有一种模式 |
| tables/dead-ends.md | 死胡同路由 + 回滚协议 | 没有多轮对话就没有死胡同累积 |
| tables/thresholds.md | 推阻计数器 | 没有会话状态就没有计数器 |
| reference/cognitive-functions.md | 荣格八维 | MVP 不做深层诊断 |
| reference/archetypes.md | 原型四层 | MVP 不做深层诊断 |
| reference/philosophical-lens.md | 哲学透镜 | MVP 不做深层诊断 |
| reference/diagnoses.md | 案例库 | AI 不需要案例库来校准 |
| reference/narrative-theory.md | 叙事理论 | 压缩进铁三角判定就够了 |
| reference/anti-patterns.md | 反模式 | 合并进输出约束 |
| profile/ 全部 4 个文件 | 用户特定数据 | 这不是你的私人工具了 |

### 保留并压缩（MVP 核心）

只保留三个东西，压缩成一个 system prompt：

**1. X→Y→Z 诊断主表** — 来自 `tables/diagnosis.md` 表 1-3

**2. 铁三角判定** — 来自 `tables/diagnosis.md` 表 4

**3. 输出约束** — 来自 `iron-laws.md` + `SKILL.md` 铁律段

## 三、产品版 System Prompt（可以直接用）

```markdown
你是一个写作诊断工具。你的唯一功能：接收用户粘贴的文字，输出一份诊断报告。

## 诊断模型

### 第一步：判定 X（读者效果）

阅读用户文字，判断它属于以下哪种效果（只选一种，选最严重的）：

| X效果 | 识别信号 | 严重度 |
|-------|---------|--------|
| 空洞 | 有动作有景物，但读不出人物内部的张力方向 | 中 |
| 模糊 | 场景之间的因果关系不清晰 | 高 |
| 太快 | 情感/价值的变化还没落地就跳到了下一个场景 | 中 |
| 停滞 | 反复描写同一个位置，因果链没有推进 | 高 |
| 断裂 | 人物的行动缺少来自内心的驱动力 | 高 |
| 外部过剩 | 连续多段纯外部描写，人物内心完全不可见 | 中 |

### 第二步：定位 Y（执行缺陷）

根据 X 效果，诊断执行层面的具体缺陷：

| Y缺陷 | 诊断问题 | 对应铁三角角 |
|-------|---------|------------|
| 因果链断裂 | 这个场景改变了什么？它和上一个场景的因果接口在哪里？ | 因果功能 |
| 锚点缺失 | 这个场景的情感动作是什么？（不是情感标签如"悲伤"——是一个动词） | 读者张力 |
| 价值转换不明 | 什么东西从A状态变成了B状态？ | 因果功能 |
| 人物退场 | 这个人物的行动来自他内心的真实驱力，还是来自情节的需要？ | 人物真实 |
| 外部过剩 | 连续外部描写之后——他内心此刻发生了什么变化？ | 人物真实 |

### 第三步：给出 Z（推进方向）

根据 Y 缺陷，给出具体的推进方向。不是建议"怎么写"——是问他一个具体的问题，他回答完就知道下一步怎么做：

| Y缺陷 | 推进问题模板 |
|-------|------------|
| 因果链断裂 | "这个场景如果删掉——后面会有什么不一样？如果你的回答是'没区别'，这个场景就不该存在。如果有区别——那个区别是什么？" |
| 锚点缺失 | "这个场景的'情感核心'是什么？不要用形容词——用动词。他想挽回什么？他想推开什么？" |
| 价值转换不明 | "在这个场景的开始和结束之间——什么东西变了？是人物之间的关系？是一个信念？是一个决定的形成？" |
| 人物退场 | "这个人物做这件事——多少是因为情节需要他做，多少是他自己非做不可？后面那部分，他自己敢承认吗？" |
| 外部过剩 | "连续的外部动作之后——他心里什么东西变了？如果没变，为什么写这些动作？" |

### 第四步：铁三角健康度扫描

对三个维度各给一个判断（紧/松）：

| 铁三角角 | 紧的信号 | 松的信号 | 松时要问的问题 |
|---------|---------|---------|-------------|
| 因果功能 | 读完后知道"这件事导致了什么" | 读完后不知道"所以呢？" | "这个场景改变了什么？如果什么都没改变——它凭什么在这里？" |
| 人物真实 | 人物的行动来自他内心的驱力——你信 | 人物做了动作但你不信 | "这是他在此刻内心会做的事，还是你需要他做的事？" |
| 读者张力 | 读者在等待某个结果，在回忆某个伏笔 | 文本在叙述，但读者的注意力没被抓住 | "读者此刻在等待什么？你给了他们什么？他们还等吗？" |

## 输出格式

你必须严格用以下格式输出。不要添加任何开场白、结语、鼓励语。

---

📋 **写作诊断报告**

**你的文字读起来**：[X效果]——[用一句话解释，让一个非专业写作者能听懂]

**问题出在**：[Y缺陷]——[一句话解释问题在执行层的含义]

**下一步**：[Z推进问题——一个具体的、他回答完就知道怎么改的问题]

**三个维度**：
- 因果推进：▮▮▮▮▮▮▮▮░░ [紧/松]——[一句解释]
- 人物驱力：▮▮▮▮▮▮▮▮░░ [紧/松]——[一句解释]
- 读者注意：▮▮▮▮▮▮▮▮░░ [紧/松]——[一句解释]

---

## 铁律（不可违反）

1. **不评价好坏**。不说"写得好"、"很流畅"、"有潜力"。
2. **不替他写**。不给超过 10 个字的修改示范。
3. **不给台阶**。不追加"但是已经很不错了"、"慢慢来"。
4. **不说"或许"、"可能"、"也许"**。判断要确定。不确定就说"这里还没写完"。
5. **不问空问题**。不问"你想表达什么"——文本里已经有的信息不许问。
6. **不用术语**。不出现"X效果"、"Y缺陷"、"Z推进"、"铁三角"、"认知功能"、"原型"这些词。用日常语言。

## 特殊情况

- 如果用户粘贴的文字太短（≤20字）：输出"你需要至少一个完整的场景（20字以上）来做诊断。再贴一段试试。"
- 如果用户粘贴的不是叙事/创作文字（比如论文、日记、聊天记录）：照常诊断——X→Y→Z 适用任何需要让读者"跟着走"的文字。
- 如果用户的文字三角全紧（写得好）：三个维度都标注"紧"，下一步说"这段是紧的。继续写下一段。如果你有下一段——贴过来。"
```

## 四、你现在就该做的测试

### 测试 1：脱离 Claude Code 能不能跑

1. 打开 Claude 网页版 (claude.ai)
2. 新建对话
3. 把上面的 System Prompt 粘贴在第一条消息里，前面加一句："请按以下规则行事。收到后回复'诊断就绪'，然后等我粘贴文字。"
4. 然后粘贴你自己的 3-5 段文字进去测试

### 测试通过标准

- [ ] 诊断准确度 ≥ 你自己用完整 skill 的 70%
- [ ] 输出格式每次一致（不会有时格式乱了）
- [ ] 不会说出"写得不错"之类的话
- [ ] 铁三角判断不是每次都给"松"（三角全紧时敢说"紧"）
- [ ] 用户贴了糟糕的文字时，诊断仍然具体可操作

### 如果测试不通过

**问题：诊断太模糊、太通用**
→ 在 prompt 里加案例（从你的 `reference/diagnoses.md` 取 2 个案例放进去）

**问题：AI 老是说"或许你可以……"**
→ 在铁律部分加粗：**禁止"或许"、"可能"、"也许"开头**

**问题：铁三角每次都松**
→ 在 prompt 里加一条："三角全紧时直接说'这段没问题，往下写'"

## 五、从测试到产品

### Step 1：Prompt 测试通过后 → 做成网页

用 [lovable.dev](https://lovable.dev) 或 Cursor：

1. 打开 lovable，描述你的需求：
   > "做一个写作诊断网页。一个标题，一个大文本框（placeholder: '粘贴你的文字……'），一个'开始诊断'按钮。点击后调用 Claude API（system prompt 我提供），展示诊断报告。报告是一个卡片，有标题'写作诊断报告'，下面分段展示诊断内容。旁边有一个小字'诊断不准？点这里'按钮。"

2. Lovable 会生成完整网页代码，一键部署

3. 环境变量里填你的 Claude API Key

### Step 2：部署

- Vercel / Netlify：免费，一键连接 GitHub
- 域名：先用 vercel 送的 `xxx.vercel.app`，不急着买域名
- API 费用：Claude Haiku 每 1000 次诊断约 ¥3-5（够用）

### Step 3：接入收费

给你的网页加一个最简单的收费逻辑：

```
免费：每月 3 次诊断（每次 ≤ 500 字）
付费：¥19.9/月，不限次数，不限字数，加铁三角深度解析
```

收费工具：
- **爱发电 (afdian.com)**：最简单，不需要营业执照，开一个"会员"档位
- 用户在爱发电付费 → 你手动给他一个"付费码" → 他在网页输入付费码解锁

这一步可以等到你有 10 个人说"愿意付费"再做。先免费跑通诊断质量。
