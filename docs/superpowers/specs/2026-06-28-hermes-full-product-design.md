## 1. 产品定位与愿景

### 一句话定位

**写作内在技能训练器** — 用户通过反复使用，将分析框架内化为写作直觉，最终不需要这个工具。

### 核心差异化

| 维度 | Hemingway | Grammarly | DeepL Write | 我们 |
|------|-----------|-----------|-------------|------|
| 分析深度 | 可读性公式（ARI） | 语法+风格 | 改写建议 | **六维焦距分析** |
| 语义理解 | ❌ 零 | 部分 | 部分 | **体裁预判+认知功能** |
| 推进方式 | 无（只高亮） | 一键替换 | 一键替换 | **指向方向，不替你走** |
| 跨文本追踪 | ❌ | ✅ (需登录) | ❌ | **松绿·惯性（匿名可）** |
| 中文原生 | ❌ | ❌ | ❌ | **✅ 中文第一等公民** |
| 能力内化 | ❌ | ❌ | ❌ | **✅ 核心目标** |

### 空白地带

**没有任何现有工具同时做到：匿名可用 + 跨会话记忆 + 跨文档追踪。** 我们填补这个空白。

### 核心哲学

> 镜子反射 = 推动。看见，才能选择要不要跨过去。
> 镜子不是导师——但镜子反射本身就是为了推动。推≠替写：门是开的，路要自己走。

## 2. Hermes 三阶段模型

```
A·赫尔墨斯（分析·镜子）
       │
       │  六维焦距扫描 → 五色信号定位
       │  输出：文本在干什么（用户在写什么）
       │
       ▼
B·赫尔墨斯（推进·教练）
       │
       │  X→Y→Z 诊断 → 指向方向
       │  输出：这里可以往 X 方向走
       │
       ▼
C·赫尔墨斯（指导·修炼）
       │
       │  松绿·惯性 → 写作指纹 → 能力雷达
       │  输出：这是你反复出现的模式（你看见了什么）
       │
       ▼
  用户内化 → 不再需要工具
```

### 三阶段关系

- **A 是基础**：没有分析就没有推进——必须先看清楚
- **B 是核心**：用户来的目的——"我卡住了，推我一把"
- **C 是长期价值**：用户留下来的原因——"我看见自己在成长"
- **三阶段不是线性**：每次使用走 A→B；C 在后台累积

## 3. L1-L5 融合架构

### 架构血统

| 层 | 名称 | 功能 | 血统 |
|----|------|------|------|
| L1 | 句子分解引擎 | Tokenize → 句型分类 → 复杂度计算 | **Hemingway 吸收** |
| L2 | 六维分析引擎 | 语言/语义/情感/结构/语用/批判/数字 | **原始核心** |
| L3 | 颜色映射引擎 | 分析结果 → 信号颜色 → 渲染指令 | **融合新生** |
| L4 | Hermes 推进引擎 | 信号 → 方向 → 动作句 | **原始核心** |
| L5 | 三模式界面 | 透视/我的文字/写作花园 | **融合新生** |

### Hemingway 吸收了什么（L1）

- 句子级拆解：将文本切分为可独立分析的句单元
- 复杂度量化：字符/词比、词/句比、句长分布
- 信号标记：每句标记句型特征（简单/复合/复杂/极长）

### Hemingway 不做什么（我们的差异化）

- 不做语义理解 → 我们的 L2 做
- 不做推进建议 → 我们的 L4 做
- 不做跨文本追踪 → 我们的 C 阶段做
- 不做用户指纹 → 我们的松绿做

### L1 → L2 → L3 数据流

```
原始文本
  │
  ▼
L1 句子分解 ──→ 句单元列表 [{text, type, complexity}, ...]
  │
  ▼
L2 六维分析 ──→ 每句分析结果 [{linguistic, semantic, structural, pragmatic, critical, digital}, ...]
  │
  ▼
L3 颜色映射 ──→ 每句颜色标记 [{sentence, colors[], gutter: [{color, signal, detail}]}]
  │
  ▼
L4 推进引擎 ──→ 诊断报告 + 动作句
  │
  ▼
L5 界面渲染
```

### L2→L3→L4 接口定义

三层之间传递的数据结构：

```
L2 输出: SentenceAnalysis[]
  └─ 每句: { linguistic, semantic, sentiment, structural, pragmatic, critical, digital }

L3 消费 SentenceAnalysis[]，追加颜色标记，输出:
  ColoredSentence[] = SentenceAnalysis + { colors: ColorSignal[], gutter: GutterBlock[] }
  └─ ColorSignal: { color, signal, detail }
      颜色标识"什么信号在哪里"，原始分析数据保留以供追溯

L4 消费 ColoredSentence[]:
  └─ 颜色告诉它"什么信号在哪里" → 聚类同色信号
  └─ 原始分析数据告诉它"为什么产生这个信号" → 按体裁透镜的 X→Y→Z 映射表生成动作句
```

**L4 对每类颜色信号的处理逻辑**：

| 输入信号 | L4 动作 | 输出格式 |
|---------|---------|---------|
| 🔴 胭脂红 | 定位卡点，提取断裂/矛盾/缺口的文本证据 | "这里停下来——[证据]，让读者感到[效果]" |
| 🟡 琥珀黄 | 统计模式频率（≥2 次同模式触发），关联文本位置 | "看见了吗——[模式]在[位置1][位置2]重复出现" |
| 🔵 钢蓝 | 搜索未展开的伏笔/意象/论点，匹配体裁透镜的方向库 | "注意——[未展开元素]可以往[方向]走" |
| 🟣 堇紫 | 揭示隐含假设/未说之物/价值预设，追问"文本依赖了什么没说出来的前提" | "想一想——文本下面还有[隐含层]" |
| ⚫ 鼠灰 | 汇总量化数据（ARI/句长/词频），作为其他信号的辅助证据 | "知道一下——[指标] = [数值]" |
| 🟢 松绿 | 对比指纹库，命中 ≥2 历史模式时标记 | "认识你自己——连续 N 次在[场景]中使用[模式]" |

**关键设计决策**：L4 不直接访问 L2——它通过 L3 的并集数据（颜色 + 原始分析）工作。这样颜色系统成为分析的统一"界面语言"，L4 不需要知道六维分析的内部实现。

## 4. 六维焦距分析引擎

### 六维定义

| 焦距 | 层次 | 分析什么 | 示例信号 |
|------|------|---------|---------|
| **语言层** (Linguistic) | 微观 | 句法、用词、节奏、修辞 | 被动语态密集、句首重复、名词化 |
| **语义层** (Semantic) | 中观 | 主题连贯性、意象链、语义场 | 意象断裂、语义漂移、关键词缺席 |
| **情感层** (Sentiment) | 中观 | 情感调性、情感转向、情感密度 | 情感突转、情感空白、情感堆叠 |
| **结构层** (Structural) | 宏观 | 文本架构、逻辑链、段落功能 | 因果断裂、并列失衡、头重脚轻 |
| **语用层** (Pragmatic) | 外部 | 读者效果、修辞目的、语境适配 | 预设读者错位、说服力衰减、语气漂移 |
| **批判层** (Critical) | 深层 | 隐含假设、权力关系、未说之物 | 隐含前提、回避话题、价值预设 |
| **数字层** (Digital) | 量化 | 可读性分数、句长分布、词频统计 | ARI、迷雾指数、型例比 |

> 注：数字层不产生独立颜色信号，数据注入其他六维作为辅助证据。

### 分析深度与 Token 预算

| 模式 | 启用维度 | Token 预算 |
|------|---------|-----------|
| 快速透视 | 语言 + 结构 | ~800t |
| 标准透视 | 语言 + 语义 + 情感 + 结构 | ~1,500t |
| 深度透视 | 全部六维 + 批判层 | ~3,000t |

## 5. 六信号颜色系统

### 设计原则

**颜色键控用户动作，不键控分析维度。** 用户看到红色不需要知道"这是语言层分析"——只需要知道"这里需要停下来看一下"。

### 六色信号

| 颜色 | 色值 | 信号 | 含义 | 触发条件 |
|------|------|------|------|---------|
| 🔴 胭脂红 | `#E03E3E` | **卡点** | 停下来。这里有什么在阻碍读者。 | 句法断裂 / 语义矛盾 / 逻辑缺口 |
| 🟡 琥珀黄 | `#D4A017` | **模式** | 看见了吗。这个模式在重复。 | 句首重复 / 句式循环 / 修辞习惯 |
| 🔵 钢蓝 | `#3B82C4` | **推进** | 注意。这里有一个可以走的方向。 | 未展开的伏笔 / 可深化的意象 / 可发展的论点 |
| 🟣 堇紫 | `#7C3AED` | **暗层** | 想一想。文本下面还有东西。 | 隐含假设 / 未说之物 / 权力关系 / 价值预设 |
| ⚫ 鼠灰 | `#6B7280` | **数据** | 知道一下。量化指标。 | 可读性分数 / 句长异常 / 词频统计 |
| 🟢 松绿 | `#10B981` | **惯性** | 认识你自己。这是你反复出现的模式。 | 跨文本指纹 ≥3 篇命中 |

### 颜色叠加规则

一句话可同时触发多种信号。渲染策略：**侧边 gutter 竖排色块标记**（像 VS Code 断点列），不染色文字本身。

```
┌──────────────────────────────────────┐
│ 🔴🟡  │ 但是我还是觉得这个事情不太对。  │  ← 同时触发卡点+模式
│ 🔵    │ 也许我应该换一个角度去看。      │  ← 仅推进
│ 🟣    │ 毕竟我们都知道这意味着什么。    │  ← 仅暗层
└──────────────────────────────────────┘
```

Gutter 色块顺序：红 → 黄 → 蓝 → 紫 → 灰 → 绿（按紧迫度降序）。

### 松绿·惯性的特殊规则

- **仅在"我的文字"模式下激活**
- **单端累计 ≥3 篇标记为"我的文字"后**，该端松绿首次亮起
- 每篇新文字分析后，对比指纹库，命中 2+ 历史模式时标记松绿
- 松绿描述格式："你连续 N 次在 [场景] 中使用 [模式]——这是你的惯性。不是要改，是要看见。"
- Phase 4 云端合并后，跨端指纹统一重新计算

### 深色模式适配（待定）

当前六色值适用于浅色背景（`#FFFFFF`）。深色模式下的适配策略在 Phase 2 Web 编辑器 UI 设计时确定，需考虑的变量：
- 饱和度调整（深色背景下同等饱和度显得更刺眼）
- 亮度补偿（胭脂红 `#E03E3E` 在 `#1E1E1E` 背景下可读性下降）
- 备选方案：为六色各准备一套深色模式色值，或使用 CSS `color-scheme` 自动调整

## 6. 模式系统

### 模式滑块

受 DeepSeek 快速模式/专家模式滑块启发：

```
┌────────────────────────────────────────────┐
│  透视这段文字  ●━━━━━━━━━━━━━━━━━○  我的文字  │
│  (不限来源)                      (记入指纹)  │
└────────────────────────────────────────────┘
```

### 透视模式（默认）

- 适用：任何文本 — 自己的、别人的、网上的、引用的
- 启用颜色：胭脂红 / 琥珀黄 / 钢蓝 / 堇紫 / 鼠灰
- **不启用**：松绿
- 不记入写作指纹
- 不跨会话保留分析历史

### 我的文字模式

- 适用：用户声明"这是我写的"
- 启用颜色：全部六色（含松绿）
- **记入写作指纹**
- 跨会话保留分析历史（本地存储）
- 松绿在 ≥3 篇后激活
- 用户可在任意端导出指纹 JSON

### 模式切换行为

- 切换不丢失当前分析结果——已渲染的颜色保留
- 从"透视"切换到"我的文字"→ 重新分析，启用松绿对比
- 从"我的文字"切换到"透视"→ 隐藏松绿标记，不删除已记录的指纹

## 7. 三端产品矩阵

```
                        Hermes 写作引擎
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   ┌─────────┐          ┌──────────┐          ┌──────────┐
   │  Skill  │          │ Web 编辑器│          │  Dashboard│
   │ 文字入口 │          │ 日常透视  │          │ 写作修炼  │
   └────┬────┘          └────┬─────┘          └────┬─────┘
        │                    │                     │
    Claude Code        浏览器访问              Web 应用内
    /text-lens         五色逐句高亮            能力雷达
    纯文本输出         推进按钮               松绿时间线
    体裁透镜            模式滑块               写作花园
        快                   中                    慢
```

### Skill（Phase 1）

- 入口：Claude Code `/text-lens`
- 输入：粘贴文本
- 输出：结构化诊断（≤500 字中文 / ≤250 词英文）
- 定位：最快路径 — 不需要浏览器、不需要登录、不需要任何东西
- 适用：写作者在写作过程中的即时光速诊断
- 技术：纯 System Prompt，零后端依赖
- 铁律：修订版（见 §11）

### Web 编辑器（Phase 2）

- 入口：浏览器（Netlify 托管）
- 输入：直接编辑或粘贴文本
- 输出：逐句五色高亮 + 诊断面板 + 推进按钮
- 定位：日常写作伴侣 — Hemingway 式的可视化体验
- 技术：React 19 + Tailwind CSS 4 + Vite 8 + Supabase Edge Function
- 特色：
  - 左侧：编辑区（带 gutter 色块）
  - 右侧：诊断面板（A·分析 + B·推进）
  - 顶部：模式滑块
  - 底部：历史面板（仅"我的文字"模式）

### Dashboard（Phase 3）

- 入口：Web 应用内 /dashboard
- 定位：长期写作修炼 — 看见自己的成长
- 核心组件：
  - **六维雷达图**：最近 10 篇的能力分布
  - **松绿时间线**：纵向追踪反复出现的模式
  - **写作花园**：每篇"我的文字"可视化为植物（萌芽→生长→开花→结果）
  - **指纹导出**：JSON / Markdown 双格式

## 8. 六项功能 Hermes 差异化设计

### 8.1 账户系统

| | Grammarly | 我们 |
|------------|-----------|------|
| 注册墙 | 第一步就撞 | **匿名先用，注册可选** |
| 身份 | 邮箱 | 邮箱 + 微信/QQ/手机（国内）+ Google/Apple（国际） |
| 核心价值 | 同步设置 | **写作指纹 = 数字身份** |

- CIAM：Logto（开源自建或云托管）
- 匿名用户有完整分析功能，注册仅解锁云端同步和跨设备
- "写作指纹比账号更重要"——指纹是身份，账号是钥匙

### 8.2 云端存储

| | Grammarly | 我们 |
|----|-----------|------|
| 存什么 | 原文+分析 | **只存指纹，不存原文** |
| 为什么 | 训练数据 | **隐私铁律：用户的文字不离开用户** |

- 原文在用户端分析，分析完成后丢弃
- 仅上传脱敏后的指纹特征向量（模式摘要 + 统计分布 + 松绿标记）
- 指纹数据端到端加密
- 用户随时可删除云端指纹，本地指纹不受影响

### 8.3 浏览器扩展

| | Grammarly | 我们 |
|----|-----------|------|
| 模式 | 被动监控（全站注入） | **用户主动调用（口袋镜子）** |
| 触发 | 自动检测文本框 | **用户选中文字 → 右键 → 透视** |

- 定位："口袋里的镜子"——需要时掏出来，不需要时不打扰
- 不自动注入、不被动监控、不读取页面内容
- 覆盖范围：`<textarea>`、`<input>`、普通 contenteditable、我们自己 Web 编辑器
- **不覆盖**：Google Docs（canvas 渲染）、Notion（自定义编辑器）、微信公众号后台（CSP 限制）——诚实标注

### 8.4 桌面 App

| | Hemingway Desktop | 我们 |
|----|------------------|------|
| 模式 | 本地文件编辑 | **离线深度修炼间** |
| AI | 无 | **本地模型（Ollama）+ 可选云端** |

- 定位：全功能离线版 — 不需要网络、不需要账户
- 内嵌本地 LLM（Ollama）做分析，零数据外泄
- 也可以连接云端 API 获取更强分析
- 本地指纹库完全离线，用户拥有全部数据
- 适用：职业作家、日记写作者、高隐私需求用户

### 8.5 文档管理·写作花园

| | Notion | 我们 |
|----|--------|------|
| 隐喻 | 文档 = 页面 | **文档 = 植物** |
| 组织 | 文件夹树 | **花园：萌芽→生长→开花→结果** |

- 每篇"我的文字"是一棵植物
- 植物状态由以下状态机驱动：

### 写作花园植物状态机

```
                    ┌──────────────────────────────┐
                    │         新文本进入             │
                    │   (用户声明"这是我的文字")      │
                    └─────────────┬────────────────┘
                                  │
                                  ▼
                    ┌─────────────────────────────┐
                    │  🌱 萌芽 (Sprout)             │
                    │  条件：patterns 数组为空       │
                    │  文本已被分析，但未检测到       │
                    │  任何可追踪的写作模式           │
                    └─────────────┬───────────────┘
                                  │
                    patterns 数组首次非空（任意 pattern 命中）
                                  │
                                  ▼
                    ┌─────────────────────────────┐
                    │  🌿 生长 (Growing)            │
                    │  条件：patterns 非空           │
                    │  但该文档自身无松绿标记         │
                    │  （全局松绿可能已激活，         │
                    │   但这篇文档未命中历史模式）     │
                    └─────────────┬───────────────┘
                                  │
                    该文档 ≥1 个 pattern 的 across_texts.length ≥ 3
                    且该 pattern.pine_green === true
                                  │
                                  ▼
                    ┌─────────────────────────────┐
                    │  🌸 开花 (Blooming)           │
                    │  条件：文档自身携带松绿标记     │
                    │  用户在此文档中看见了自己的惯性  │
                    │  （不要求全局松绿激活，         │
                    │   单文档可独立开花）            │
                    └─────────────┬───────────────┘
                                  │
                    用户主动标记"我打破了这个模式"
                    或 系统检测：下次分析该模式不再出现 + 用户确认
                                  │
                                  ▼
                    ┌─────────────────────────────┐
                    │  🍊 结果 (Fruiting)           │
                    │  条件：用户确认打破惯性模式     │
                    │  触发方式：系统提示             │
                    │  "你连续 N 次出现的[模式]      │
                    │   这次没有出现——是你有意为之吗？"│
                    │  用户确认 → 结果               │
                    └─────────────────────────────┘
```

**状态转换规则**：
- 每次分析后重新计算植物状态（状态可升可降——如果用户回退到旧模式，开花可降为生长）
- 🌱→🌿：自动（patterns 数组非空即触发）
- 🌿→🌸：自动（松绿标记出现即触发）
- 🌸→🍊：**需用户确认**（不自动触发——"打破"是一个有意识的动作，不是算法的判断）
- 🍊→🌸：如果同一模式重新出现，结果降级回开花

**缩放机制**（≥50 篇自动触发）：
  - 季度花园归档
  - "活跃植物"筛选（最近 30 天有更新的）
  - 年度写作森林总览

### 8.6 导出

| | Grammarly | 我们 |
|----|-----------|------|
| 导出什么 | 报告 PDF | **指纹 JSON + 写作护照 Markdown** |

- **指纹 JSON**（机器可读）：完整写作指纹数据，可导入其他端或其他工具
- **写作护照 Markdown**（人类可读）：你的写作模式摘要 + 松绿时间线 + 六维雷达数据
- **数据主权**：用户拥有自己的写作指纹——随时导出、随时删除、随时迁移
- 指纹格式是开放的——任何人可以写工具来读取和可视化

## 10. 七体裁透镜 × 六维焦距映射

### 判定顺序

**体裁先、焦距后。** 先判定"这是什么类型的文本"，再在体裁框架内跑六维焦距分析。

### 体裁→焦距优先级矩阵

| 体裁 | 语言层 | 语义层 | 情感层 | 结构层 | 语用层 | 批判层 |
|------|--------|--------|--------|--------|--------|--------|
| **诗性/意象** | ★★★ | ★★★ | ★★ | ★ | ★ | ★★ |
| **叙事/故事** | ★★ | ★★ | ★★★ | ★★★ | ★★ | ★ |
| **论述/观点** | ★ | ★★ | ★ | ★★★ | ★★★ | ★★★ |
| **技术/学术** | ★★★ | ★★ | ★ | ★★★ | ★★ | ★ |
| **对话/交流** | ★★ | ★★ | ★★★ | ★ | ★★★ | ★★ |
| **日记/内省** | ★ | ★★ | ★★★ | ★ | ★ | ★★ |
| **创意/混合** | ★★ | ★★ | ★★ | ★★ | ★★ | ★★ |
| **通用（兜底）** | ★★ | ★★ | ★★ | ★★ | ★★ | ★ |

> ★★★ = 该体裁下最高优先级的焦距，必须启用
> ★★ = 推荐启用
> ★ = 可选，当文本有明显信号时启用

### 各焦距在体裁透镜中的体现

每个透镜文件（`lenses/{genre}.md`）内的 X/Y/Z 映射表，内嵌对应焦距的分析指令。例如：

- **叙事透镜**的结构层指令："定位因果链——从 X 到 Y 的转变是在哪个句子上发生的？"
- **诗性透镜**的语义层指令："追踪意象链——'镜光浮影'之后，下一个意象落在了哪里？"
- **论述透镜**的批判层指令："检查隐含前提——这个推理依赖了什么没有说出来的假设？"

### 后续行动

## 11. 铁律（修订版）

### 修订说明

v5.0.1 铁律的核心问题是：**"镜子不是导师"被过度解读为"镜子不推"。** 本次修订澄清：镜子反射 = 推动——看见本身就是推动。铁律保留"不替你走"的底线，但不再限制"指出方向"。

### 修订后铁律

| # | 铁律 | 说明 | 变更 |
|---|------|------|------|
| 0 | **示范豁免**：需要 ≤15 字微型示范来让方向变得具体可感时可用 | 覆盖铁律 1 | 保留 |
| 1 | 不替用户写超过一句话 | 示范是为了让方向可感，不是为了替写 | 保留 |
| 2 | 不评价好坏 | 不说"写得好"、"这段很流畅"——镜子不评判 | 保留 |
| 3 | 不给空鼓励 | 不说"慢慢来"、"你已经很棒了"——推进比安慰有用 | 保留 |
| 4 | 不假装是用户 | 说你的话，不替他感受 | 保留 |
| 5 | 每次开口必须带有文本诊断 | 没有诊断就不说话 | 保留 |
| 6 | 不问空问题 | 答案已在文本里的问题不许问 | 保留 |
| 7 | 指向文本，不指向人格 | 说"这段文字让读者感到……"，不说"你是……的人" | 保留 |
| 8 | 认知功能诊断结果默认不宣示标签 | 只说现象，不贴认知类型标签 | 保留 |
| **9** | **推≠替写** | **给方向不给答案。"这里可以往 X 走"是推，"这里应该写成 X"是替写。门是开的，路自己走。** | **新增** |
| **10** | **动作句优先** | **推进建议用"X 在这里是可能的"而非"你应该做 X"。保留镜子的不强制语气。** | **新增** |

## 12. 跨端指纹存储方案

### 整体策略：先客户端，后云端

```
Phase 1-3（无账户阶段）
    │
    ├── Skill 端：~/.claude/text-lens/fingerprint.json
    ├── Web 端：localStorage fingerprint JSON
    └── Obsidian 端：vault/.text-lens/fingerprint.json
           │
           │ 各端独立计数，独立亮松绿
           │ 用户可手动导出/导入 JSON 合并
           │
Phase 4（账户上线）
           │
           ▼
    云端指纹同步
    · 用户可选"关联匿名指纹到账户"
    · 三端 fingerprint 自动合并去重
    · 松绿阈值在合并后重新计算
```

### 松绿激活逻辑

```
任一端的本地指纹累计 ≥ 3 篇 → 该端松绿激活
跨端手动合并后 ≥ 3 篇 → 合并后各端松绿全部激活
Phase 4 云端合并 → 全端统一松绿
```

### 指纹 JSON 结构

```json
{
  "fingerprint_id": "fp_abc123",
  "created": "2026-06-28T10:00:00Z",
  "updated": "2026-06-28T14:30:00Z",
  "texts_analyzed": 5,
  "patterns": [
    {
      "id": "pat_001",
      "type": "sentence_starter_repetition",
      "trigger": "段落开头重复使用'但是'",
      "frequency": 0.6,
      "first_seen": "2026-06-15",
      "last_seen": "2026-06-28",
      "across_texts": ["text_001", "text_003", "text_005"],
      "pine_green": true
    }
  ],
  "dimension_profile": {
    "linguistic": { "avg_sentence_length": 28.5, "passive_ratio": 0.12 },
    "sentiment": { "dominant": "reflective", "volatility": 0.3 },
    "structural": { "preferred_opening": "thesis_first", "closure_style": "abrupt" }
  }
}
```

### 手动合并规则

- 用户从 A 端导出 `fingerprint.json`，拖到 B 端的指纹目录
- B 端检测到导入文件 → 对比 `fingerprint_id` → 合并不重复的 texts_analyzed 和 patterns
- 合并后如果 patterns 累积命中 ≥ 3 篇，松绿激活
- 冲突策略：同 pattern 以 `last_seen` 更晚的为准

## 14. 开发阶段规划

### 优先级重排（基于用户价值密度 × 实施成本）

原设计文档中的编号顺序是"建议"而非"必须"。真正优先级由两个因素决定：**用户价值密度**（谁对用户价值最大）和 **实施成本**（谁开发周期最短）。

| 优先级 | 阶段 | 用户价值密度 | 实施成本 | 理由 |
|--------|------|-------------|---------|------|
| **P0 最高** | Phase 1 — Skill 发布 | 高 | 低 | 最快验证核心假设，零后端依赖 |
| **P1 次高** | Phase 2 — Web 编辑器 | 最高 | 中 | 触达用户最多，验证核心交互 |
| **⏸️ 暂停** | Phase 3 — Dashboard | 中高 | 中高 | 依赖 Phase 2 指纹积累。Phase 2 验证失败则降低优先级 |
| **⏸️ 暂停** | Phase 5 — 浏览器扩展 | 低 | 中低 | 安装门槛高，用户价值密度最低 |
| **⏸️ 暂停** | Phase 6 — 桌面 App | 低 | 最高 | 开发周期最长，受众最窄，与 Obsidian 插件重叠 |
| **后续** | Phase 7 — Obsidian 插件 | 高 | 中 | 精准触达 Obsidian 用户 |
| **后续** | Phase 8 — MCP Server | 中低 | 低 | 分发效率高，但需要已有端被使用 |
| **延后** | Phase 4 — 账户系统 | 中 | 最高 | 双区域 + Logto + 同步，开发成本最高。Phase 2 验证成功后再做 |

### 核心原则

```
Phase 1 → Phase 2 → 停一下，收集反馈 → 决定下一步
```

- **不要同时做两个端**：每个端需要完整的开发→测试→反馈闭环
- **Phase 4（账户系统）推迟到最后**：除非真实用户需要跨端同步，否则 Logto 的复杂性和成本是当前阶段应避免的
- **Phase 2 完成后重新评估 Phase 3-8**：用户反馈可能推翻设计假设
